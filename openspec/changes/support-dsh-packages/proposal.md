# Proposal

## Why

Every package in this workspace is a Pi extension today: a root-level `pi-<topic>/` directory with a `pi` manifest, no build step, and a release plan that proves the packed tarball by loading it in Pi. The owner's dsh (DeepSeek Harness) plugin `@indexyz/dsh-autocompact` lives in the sibling repository `dsh-agent-extensions`, whose workspace, lockfile, and scripts (`scripts/check-workspace-versions.mjs`, `pack:autocompact`) duplicate this repository's model without its release engine. Moving it here needs one thing the repository does not have: a package class that is not a Pi package. It carries a `dsh` manifest instead of a `pi` manifest, it builds (the host half with `tsc` into `lib/`, the client half with `tsdown` into a root `client.js` that the Harness web module loader fetches), its built artifacts are committed because a local `link:` install consumes them, and the release plan's unavoidable step — install the tarball and load it in Pi (`pi -ne -e <installed> --mode rpc` + `get_commands`) — cannot verify it at all. This change adds that class and the smallest extension of the release engine that keeps every non-private workspace package under a real verification before it is uploaded.

## What Changes

- **A second package class: root-level `dsh-<topic>/` packages.** A dsh package is a root-level `dsh-<topic>/` workspace directory published as `@indexyz/dsh-<topic>` with a `dsh` manifest (`dsh.bundle.patch`, `dsh.client`) and no `pi` manifest, its `@deepseek-ai/*` host packages pinned in `devDependencies` and declared `"*"` in `peerDependencies` (the analogue of rule 3 for `@earendil-works/*`), a `files` allowlist that ships the built artifacts, `publishConfig.access: "public"`, and its own `tsconfig.json`, `tsconfig.build.json`, `tsdown.config.ts`, `vitest.config.ts`, and `openspec/`. The root `workspaces` array gains the directory; the root `pi.extensions` manifest does not, because a dsh package is not a Pi extension.
- **Both halves build, and their output is committed.** The package's `build` script runs `tsc -p tsconfig.build.json` (host half into `lib/`) and `tsdown` (client half into `client.js`); its `check` runs `typecheck`, `build`, then `test`, and a `link:` install of the package directory serves exactly the committed `lib/index.js` and `client.js`. Generated output is never linted or formatted: `.oxlintrc.json` and `.oxfmtrc.json` ignore `dsh-*/lib/**` and `dsh-*/client.js`.
- **A declared release smoke check.** A package manifest gains an optional `release: { "smoke": "<path relative to the package, ending in .ts>" }`. A package with a `dsh` manifest is installed with `--legacy-peer-deps` in addition to `--omit=peer`, because npm resolves its `"*"` host peers against the registry while installing and rejects the tarball when those prereleases conflict; every other package's install is unchanged. When a declared script is present, the plan installs the tarball into an empty directory and then runs `node <worktree>/<package>/<smoke> <installed-package-dir>`, requiring exit status 0 and taking the script's own output (its stderr, or its stdout when stderr is empty) as the failure detail; when it is absent, the existing Pi load is unchanged. A declared script takes precedence over Pi resources, so a package can choose its own check; a package that declares neither Pi resources nor `release.smoke` fails the plan, because nothing can verify its installed tarball. Nothing else about publication changes.
- **A dated changelog heading is that version's section.** `scripts/release/changelog.ts` reads `## <version>` and `## <version> - <YYYY-MM-DD>` alike, so the dated history the six Pi packages carry, and the first section of the new package, name their version instead of nothing: the upload check and the Release recording work for them, while a heading carrying anything else after the version still matches nothing. This supersedes the `adopt-independent-package-releases` change, which states that a dated heading matches no version.
- **A Release for a tag that already existed names no target commitish.** The record step passes the version commit as the Release's target only for a tag the same run created. GitHub requires the `workflows` permission — one a GitHub Actions token can never hold — for a Release that names a target SHA whose comparison with the default branch touches `.github/workflows/**`, which is why the six `0.1.43` Releases the dated sections now name answered `HTTP 403: Resource not accessible by integration`: `b997bd2` predates the adoption merge's workflow changes. A tag the version already carries fixes the Release's commit by itself, so those Releases are created from their tags. The same restriction is why CI cannot create a tag at a commit that predates a workflow change, and `docs/releases.md` states both.
- **The root `check` builds every package that declares a build.** `npm run check` becomes `format:check && lint && typecheck && npm run build --workspaces --if-present && test && test:scripts`, with a root `build` script (`npm run build --workspaces --if-present`) so the committed artifacts are rebuilt before the tests that consume them, and cannot silently rot.
- **The release documentation covers seven packages in two classes.** `docs/releases.md` no longer counts six packages, its activation table checks the trusted publisher of every published package including a new one after its first manual publish, it gains a "Packages Pi does not load" section for the package a Pi load cannot verify, and its existing "First release of a new package" bootstrap covers `@indexyz/dsh-autocompact` as it stands, because npm binds a trusted publisher in an existing package's settings; `docs/architecture.md`, `docs/workflow.md`, `AGENTS.md`, the root `README.md`, and `openspec/config.yaml` describe the second class instead of one.
- **Unchanged for the six Pi packages.** Their manifests, sources, versions, intents, tags, Releases, and in-Pi load are untouched: the smoke field is optional, no `pi-*` manifest changes, no workflow changes, and nothing about how a version is chosen, planned, uploaded, tagged, or recorded changes.

## Capabilities

### New Capabilities

- `dsh-packages`: what a root-level `dsh-<topic>/` package is, how its two halves are built and committed, how the root tooling treats its generated artifacts and its build, and how it is verified, versioned, and published like every other non-private workspace package.

### Modified Capabilities

- `package-releases`: the plan's install-and-verify step becomes a choice between the existing Pi load and a check the package declares in its manifest. That capability is introduced by the pending `adopt-independent-package-releases` change, which is not archived yet, so `openspec/specs/package-releases/spec.md` does not exist and this change writes its share of the capability as additions.
- `agent-guidance` and `agent-release-workflow`: the instruction surface and the runbook must describe two package classes and seven packages. Same base (`openspec/specs/` is empty), so those deltas are additions too.

## Impact

- **Root tooling:** `package.json` (a `dsh-autocompact` entry in `workspaces`, a new `build` script, `check` gaining it), `.oxlintrc.json` and `.oxfmtrc.json` (generated dsh output ignored), and `openspec/config.yaml` (the repository paragraph counts seven packages in two classes).
- **Release engine:** `scripts/release/json.ts` (the `release.smoke` field), `scripts/release/plan-core.ts` (`smokeCheck`: declared script, Pi resources, or a hard failure), `scripts/release/build.ts` (run the declared script instead of the Pi load when one is declared), `scripts/release/changelog.ts` (a dated section heading names its version), `scripts/release/github.ts` and `scripts/release/publish-core.ts` (a Release for an existing tag names no target commitish), and `scripts/release/test/manifest.test.ts`, `scripts/release/test/changelog.test.ts`, `scripts/release/test/publish-record.test.ts`, plus `scripts/release/test/publish-world.ts`. No change to `scripts/release/plan.ts`, `gate.ts`, `publish.ts`, or `.github/workflows/`.
- **Packages:** the new `dsh-autocompact/` package (its own change), one row in the root `README.md` package table, and the six `pi-*` packages unchanged.
- **Documentation:** `AGENTS.md` (the package rules now cover both directory prefixes), `docs/architecture.md`, `docs/workflow.md`, `docs/releases.md`, and the root `README.md`.
- **Release decision:** one hand-written `none` intent for `@indexyz/dsh-autocompact`. Root tooling, docs, and tests need no decision, and no `pi-*` package's published files change, so the six Pi packages get none.
- **Published artifacts:** `@indexyz/dsh-autocompact@0.1.0` becomes an upload on the first push to `main` that carries it. npm cannot accept a first upload from CI, so the owner publishes that artifact once by hand and then adds its trusted publisher (the existing bootstrap); agents never perform that step.
