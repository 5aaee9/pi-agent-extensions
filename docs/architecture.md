# Architecture

## Repository layout

```
.
├── AGENTS.md                      rules and index for agents
├── CLAUDE.md                      redirect to AGENTS.md
├── README.md                      human overview and package table
├── LICENSE                        MIT
├── docs/                          this documentation (releases.md is the release runbook)
├── openspec/                      OpenSpec root for repository-wide changes
├── .changeset/                    release intents (<id>.md), changesets config, changelog renderer
├── .github/workflows/             lint.yml (checks, release-impact gate) and publish.yml (publication)
├── scripts/
│   └── release/                   release-impact gate, publication plan and publish steps, and their tests (TypeScript)
├── .agents/skills/
│   ├── pi-extension-dev/SKILL.md  skill loaded when working on an extension
│   └── openspec-*/                OpenSpec workflow skills (generated by openspec init)
├── .claude -> .agents             symlink, so Claude Code reads the shared skills
├── pi-<topic>/                    one Pi package per root-level directory, published as @indexyz/pi-<topic>
├── package.json                   workspace root (private): workspaces, scripts, root dev tooling, pi manifest
├── package-lock.json              the only lockfile
├── tsconfig.json                  strictest compiler settings for scripts/ and .changeset/ (typecheck only)
├── .oxlintrc.json                 repository-wide lint rules
├── .oxlintrc.tooling.json         strict type-aware lint profile for scripts/ and .changeset/
└── .oxfmtrc.json                  formatter settings
```

The packages today are `pi-provider-sub2api`, `pi-custom-provider`, `pi-continue`, `pi-skill`, `pi-model-trace`, and `pi-autocompact`; the root `package.json` lists them in `workspaces`.

Agent-facing files follow one rule: `AGENTS.md` and `.agents/` are the shared, harness-neutral surface. `.claude` is only a symlink to `.agents`, and `CLAUDE.md` contains nothing but `@AGENTS.md`. No harness gets files of its own.

The root never contains extension runtime code. It provides the workspace (one `npm install` for every package), oxlint and oxfmt for the whole tree, the changesets CLI for release intents and versions, and the release tooling in `scripts/release/`, which Node runs directly from TypeScript (type stripping; there is no build step). Nothing at the root is published or loaded by Pi. Everything a package needs to typecheck and test lives in the package itself.

## Package anatomy

```
pi-<topic>/
├── package.json        @indexyz/pi-<topic>, version, files allowlist, pi manifest, scripts, peer and dev dependencies
├── README.md           what it does, how to install, commands and configuration it provides
├── CHANGELOG.md        release notes; new sections are written by `changeset version` and reviewed
├── LICENSE             MIT, shipped in the tarball
├── index.ts            extension entry: default export function (pi: ExtensionAPI)
├── *.ts                implementation modules next to index.ts, kept free of Pi API where possible
├── data/               optional bundled data (pi-model-trace ships data/unified_bank.json)
├── test/
│   └── *.test.ts       Vitest tests
├── tsconfig.json       the package's strict compiler settings (noEmit; typecheck only)
├── vitest.config.ts    the package's test configuration
└── openspec/           the package's own OpenSpec root: specs/ and changes/
```

Rules that follow from this layout:

- `index.ts` is the entry Pi loads (`pi.extensions: ["./index.ts"]`). It wires registrations (`pi.registerCommand`, `pi.registerProvider`, `pi.on`, ...) to implementation modules.
- Logic that does not need `ExtensionAPI` lives in separate modules and gets unit tests under `test/`.
- Relative imports use the `.ts` extension (`import { loadProviders } from "./config.ts"`). Pi loads sources directly and each `tsconfig.json` sets `allowImportingTsExtensions`.
- `files` lists every shipped file explicitly (each `.ts` module, `README.md`, `CHANGELOG.md`, `LICENSE`, data files). A new module that is not added to `files` is missing from the published package; the publication plan rejects a tarball that lacks a declared file.
- `test/`, `tsconfig.json`, `vitest.config.ts`, and `openspec/` are never in `files`.

## Package scripts and tooling

Every package defines the same scripts: `test` (`vitest run`), `test:watch`, `typecheck` (`tsc --noEmit`), `check` (typecheck and tests), and `prepack` (`npm run check`, so packing a package always runs its own checks). The root scripts fan out with `--workspaces`: `npm run typecheck` and `npm test` run every package's script.

Each package's `devDependencies` pin the Pi host packages it builds against, plus `typescript`, `vitest`, and `@types/node`. Pinned Pi versions may differ between packages (`docs/pi-reference.md`); npm then installs the differing version inside that package's own `node_modules/`.

## OpenSpec roots

OpenSpec resolves its root by walking up from the working directory to the nearest `openspec/` directory. The repository uses two levels:

| Root                          | Covers                                                                 |
| ----------------------------- | ---------------------------------------------------------------------- |
| `openspec/` (repository root) | root tooling, workflows, release tooling, docs, conventions, AGENTS.md |
| `<name>/openspec/`            | everything about that one extension                                    |

Specs describe the current behavior of the thing in their root, so a package's specs stay with the package and the root never accumulates specs for code it does not contain.

## Manifest and dependencies

- `name` is always `@indexyz/<directory name>`.
- `publishConfig.access` is `public` because scoped packages are private on npm by default. `repository.url` and `repository.directory` name this repository and the package directory; npm provenance checks the URL.
- `pi.extensions` points at `./index.ts`.
- Host-provided packages are `peerDependencies` with `"*"` and exact pins in `devDependencies`. List only the ones the package imports.
- Real runtime dependencies would go in the package's `dependencies`, never the root. Installed packages load from their own directory, so a package may not rely on another package's dependencies.
- `engines.node` is `>=22.19.0`.
- The root `package.json` is private and carries a `pi` manifest listing every `./pi-*/index.ts`, so installing the whole repository from git loads every package.

## Release records

Release state lives in committed files and in the registry, never in CI configuration: release intents in `.changeset/<id>.md`, each package's version in its `package.json`, and its `CHANGELOG.md`. A push to `main` publishes every package version that npm does not have yet, built from the commit that introduced that version, and records each published version with a `@indexyz/<name>@<version>` tag and a GitHub Release. `docs/releases.md` has the procedure.

## How Pi loads a package

Pi reads `package.json`, resolves the `pi` manifest, and imports each extension entry from TypeScript source. There is no build step and no `dist/`. The default export runs once per extension runtime; a `/reload` replaces the runtime. Because loading happens in-process, an extension has the same permissions as Pi itself.

The full contract (lifecycle, events, commands, providers, UI, errors) is in Pi's own documentation; see `docs/pi-reference.md` for where to find it.
