# Design

## Context

See `proposal.md` for the motivation. The facts that shape the approach:

- The workspace is npm (`package-lock.json`, `npm ci`, `npm --workspace`), with six publishable packages in root-level directories (`pi-provider-sub2api/`, `pi-custom-provider/`, `pi-continue/`, `pi-skill/`, `pi-model-trace/`, `pi-autocompact/`) listed in `workspaces`. Each package owns its `tsconfig.json`, `vitest.config.ts`, and dev dependencies; the pinned `@earendil-works/*` versions differ per package (`0.87.1` in `pi-autocompact`, `0.84.0` elsewhere), so after `npm ci` the root `node_modules/.bin/pi` is Pi 0.84.0 and `pi-autocompact/node_modules/.bin/pi` is 0.87.1. The root provides oxlint and oxfmt. Pi loads the TypeScript sources directly; there is no build.
- All six packages are published at `0.1.43` under `@indexyz` with npm trusted publishers bound to `5aaee9/pi-agent-extensions` and the workflow file `publish.yml` (the current workflow has no `environment`, so the publishers have none either). npm trusted publishing binds owner, repository, and workflow file name only; it does not bind the trigger, the package manager, or package directories.
- Releases so far are `chore(release): prepare packages X` commits pushed straight to `main`, followed by a `vX` tag that runs `publish.yml`; `v0.1.43` points at `b997bd2`. The default branch has no protection rules; squash, merge, and rebase merges are all enabled. Two external pull requests have been merged; the second (`52e5517`, "fix(sub2api): restore cache hit rate in custom footer") landed after `0.1.43` and changed `pi-provider-sub2api/footer.ts`, published content that has no release yet.
- The reference repository (`/Volumes/Git/pi-extensions`) uses pnpm's native versioning: `.changeset/*.md` intents, `pnpm version -r`, an append-only `.changeset/ledger.yaml`, and about 2,700 lines of bespoke release tooling that derives CI's publication batch from the ledger records a squash/merge commit adds relative to its first parent, with authorization-continuity and withdrawal rules. Its agent documentation (`AGENTS.md`, `docs/*.md`, `pi-extension-dev` skill) is the model for the documentation added here.
- `@changesets/cli` 3.0.3 (September 2026) reads the same `.changeset/<id>.md` format pnpm uses, accepts `none` bumps, versions and writes changelogs per package, and requires `npm >= 10.9.0` and Node 22 or 24 (CI uses Node 24 with npm 11). Its `status --since` command fails only when there are changed packages and zero changesets anywhere, so it is not a per-package coverage gate. Its publishing side (`publish-plan`, `pack`, `publish`, `git-tag`) always works from the checked-out tree, tags that commit, skips any existing tag name without checking where it points, and creates annotated tags that need a Git identity; the design uses changesets for versioning only and publishes from committed snapshots with its own small scripts (Decision 2).

## Goals / Non-Goals

**Goals:**

- Publish only packages with a reviewed, prepared new version, from `main`, through the existing `publish.yml` trusted publishers, with no npm-side reconfiguration.
- Keep the agent in charge of what ships and what the notes say; CI executes and records.
- Make every published artifact and every record (tag, GitHub Release) a function of the commit that introduced the version, so that any rerun converges on "every published version is uploaded from its own snapshot, tagged, and announced" without a ledger.
- Add the smallest repository-specific tooling that closes the gaps the chosen library leaves (per-package release-impact gate, snapshot-based plan, upload, and record steps).
- Give agents one truthful instruction surface for this repository, merged from the reference repository's documents.

**Non-Goals:**

- Changing the package manager, hoisting per-package dev tooling to the root, replacing oxlint/oxfmt with Biome, or moving packages under `packages/`. These are orthogonal to releasing and would churn every manifest, URL, and lockfile for no release benefit; they can be proposed separately.
- A ledger, first-parent batch derivation, authorization-continuity checks, or a withdrawal protocol. They exist in the reference to make "publish exactly the records a merge added" safe under branch protection; this repository publishes "versions absent from the registry" (which its current workflow already does) and has no branch protection to lean on.
- Prereleases, snapshot releases, fixed or linked version groups, automatic "Version Packages" pull requests, or any live publication during this change.

## Decisions

### 1. Stay on npm and adopt `@changesets/cli` for intents, versions, and changelogs

**Choice:** add `@changesets/cli` (plus `@changesets/read` and `@changesets/parse`, which the gate and the plan step use to read intent files) as root dev dependencies; keep npm, `package-lock.json`, `npm ci`, and `npm publish` under the hood. Changesets owns the versioning side (`add`, `status`, `version`); publication is done by the repository's own scripts (Decision 2), which select each version's snapshot themselves and drive `npm publish` directly.

**Why:** changesets is the established implementation of exactly this model (intent files, independent versions, per-package changelogs), the format is byte-compatible with pnpm's native intents (so the two repositories read the same `.changeset/*.md` files), and it leaves this repository's package manager, lockfile, CI cache, and contributor workflow untouched.

**Alternatives rejected:**

- _Migrate to pnpm and port the reference's `tools/release`._ The ledger and its continuity checks are the reason that tooling exists; without pnpm's ledger the port has nothing to read. The migration touches every workflow step, the lockfile, and contributor instructions, for a release model this repository does not need.
- _Hand-written scripts only (bump, changelog, publish)._ Reimplements what changesets already does and tests; the user's principles say to lean on established libraries.
- _Changesets' `publish-plan` / `pack` / `publish --from-pack-dir` for publication._ `pack` packs the checked-out tree, so a retry after a failed upload would ship whatever `main` holds at retry time under the earlier prepared version. `publish --from-pack-dir` could upload tarballs packed elsewhere, but then changesets would only wrap `npm publish` behind a plan file format it marks experimental, while snapshot selection, sequential upload handling, and tag targets would still have to be the repository's own. Driving `npm publish` directly is a few dozen lines around `git`, `npm pack`, `npm publish`, and `gh`, with one stable plan file of the repository's own.

**One intent file names exactly one package.** `changeset version --ignore` throws on a "mixed changeset" whose file names both an ignored and a non-ignored package, so subset preparation only works when every intent names a single package. A change that affects two packages records two files (`npm run change -- --patch @indexyz/pi-a -m "..."` twice, never `--patch a,b`). The gate rejects an intent naming more than one package.

**`changeset status` is a local command, not a CI check.** It exits non-zero whenever any package file changed relative to `main` and no intent exists anywhere, so it would fail tests-only pull requests, release preparations (whose intents were just consumed), and this change itself (package `openspec/` directories count as package changes). Agents use `npm run change:status` locally to list pending intents and the versions they imply; CI validates intent files through the gate and the plan step instead (`readChangesets` throws on malformed front matter; release names are checked against the workspace package names).

**Configuration (`.changeset/config.json`):** `baseBranch: "main"`, `access: "public"`, `commit: false`, `privatePackages: { version: false, tag: false }` (the root is private and therefore never versioned, tagged, or published), `changedFilePatterns` left at the default (coverage is decided by the gate, not by `status`), `format: false` so generated changelog text is never rewritten by a formatter, and `changelog` pointing at a local module `.changeset/changelog.ts` that exports both `getReleaseLine` (renders `- <summary>` with continuation lines indented, matching the existing bullet style and omitting the commit-hash prefix of the default renderer) and `getDependencyReleaseLine` (returns an empty string; the packages have no dependencies on each other). Changelog sections therefore read `## 0.1.44` followed by `### Patch Changes` / `### Minor Changes` lists; existing `## 0.1.43 - 2026-10-11` sections stay untouched because changesets inserts above the first version heading it finds. A `none` intent produces no section and no version change and is deleted by the next `changeset version`. `changeset version` does not touch `package-lock.json`, whose workspace entries record each package's version; `npm ci` tolerates the stale entry, but the preparation runs `npm install --package-lock-only` afterwards so the lockfile stays in sync (only the bumped packages' `version` entries change).

**Root scripts:** `change` (`changeset add`), `change:status` (`changeset status`), `release:version` (`changeset version`), `release:gate` (the gate script), and `test:scripts` (`node --test "scripts/release/test/*.test.ts"`; Node 24 does not accept a bare directory). `check:versions` and the six `pack:*` scripts are removed; `check` becomes `format:check && lint && typecheck && test && test:scripts`.

### 2. Publication is "versions absent from the registry", built and recorded from each version's own commit

**Choice:** `publish.yml` runs on `push` to `main` and on `workflow_dispatch` with no inputs. Its first step requires `github.ref` to be `refs/heads/main` (a dispatch from any other branch or tag fails before anything else runs), and its concurrency group is the constant `npm-release` with `cancel-in-progress: false`. Workflow-level `permissions` is `{}`; each job declares its own. Both jobs check out `github.sha` with `fetch-depth: 0` (the scripts read history and create worktrees at older commits).

**The version commit.** For a package at version `v`, the version commit is the newest commit on the first-parent history of the checked-out commit whose `<pkg>/package.json` parses to version `v` while its first parent's copy parses to a different version or does not exist. It is found by walking `git log --first-parent --format=%H -- <pkg>/package.json` and comparing the parsed `version` of `<sha>:<pkg>/package.json` with that of `<sha>^:<pkg>/package.json`; a commit that only reformats the manifest is never a candidate, and the lookup does not depend on JSON spacing. For a squash or merge commit this is the integration commit; for a rebase merge it is the commit that touched the manifest. For every package today it resolves `0.1.43` to `b997bd2`, the commit `v0.1.43` points at, so the first run after adoption creates the six `@indexyz/<name>@0.1.43` tags there without any manual backfill. Everything about a version is taken from its version commit: the tarball, the changelog section, the tag target, and the Release notes; the one exception is an accepted existing tag at another commit carrying the version, whose Release follows the tag's commit (the _record commit_, below). For an upload no tag exists yet, so its record commit is its version commit. A later commit on `main` that changes the package without changing its version (ordinary feature work with its own pending intent) never changes what version `v` publishes.

1. **`plan`** (permissions `contents: read`; `GH_TOKEN: ${{ github.token }}` for read-only `gh` calls; no OIDC): `npm ci`, `npm run check` (the quality gate for `main` itself), then `node scripts/release/plan.ts --out <dir>`:
   - validates every intent file on disk (parseable, exactly one release, a workspace package name, a summary);
   - for every publishable package reads its current version, its version commit, whether the version is on the registry (`npm view <name>@<version> version`: a 404 means absent; any other failure fails the job), the state of its tag `@indexyz/<name>@<version>` (missing, or existing: resolved with `git rev-parse <tag>^{commit}` after fetching tags; an existing tag is accepted when its commit's `package.json` parses to that version, which covers the version commit itself and a later revert to a published version; a tag pointing at a commit that does not carry the version is a corrupted record and fails the plan), its _record commit_ (the accepted existing tag's commit when a tag exists, otherwise the version commit), the state of its GitHub Release (`gh release view`: missing or present; other errors fail), and whether `<record commit>:<pkg>/CHANGELOG.md` has exactly one non-empty `## <version>` section;
   - the **uploads** are the packages whose version is absent from the registry; each must have the exact changelog section. For each upload it creates `git worktree add <work>/<pkg> <version commit>`, runs `npm ci` there, packs with `npm pack --workspace <name> --pack-destination <dir> --json` (the package's `prepack` runs its typecheck and tests on that snapshot), checks that the tarball lists `package.json`, `README.md`, `CHANGELOG.md`, `LICENSE`, every file of the `files` allowlist and `pi` manifest, and nothing under `test/` or `openspec/`, and smoke-loads the installed tarball: `npm install --omit=peer --no-package-lock <tgz>` into a scratch directory (peers are never installed, so the host packages are not duplicated next to the extension), then `<pi> -ne -e <scratch>/node_modules/@indexyz/<name> --mode rpc` answering `get_commands` with `PI_OFFLINE=1` and `PI_CODING_AGENT_DIR` pointing at an empty directory, where `<pi>` is the worktree's `<pkg>/node_modules/.bin/pi` when the package pins its own host version and the worktree's root `node_modules/.bin/pi` otherwise; it records the tarball's SHA-256 and removes the worktree;
   - the **record work** is every package whose version is on the registry (or is an upload) and whose tag is missing, or whose Release is missing while the exact section exists (a version without such a section, like the pre-adoption `0.1.43` entries, is tag work once and never Release work, so a docs-only push after the first run stays a no-op);
   - writes `release-plan.json` (uploads with tarball names and hashes, record work, version commits) and `publish=true` to the job outputs when there is at least one upload or one item of record work, and uploads `<dir>` as the `release-batch` artifact in that case.

   Any failure blocks the whole batch; a push with nothing to upload and nothing to record ends here successfully.

2. **`publish`** (`needs: plan`, `if: needs.plan.outputs.publish == 'true'`, permissions `contents: write` and `id-token: write`, the only job with OIDC, `GH_TOKEN: ${{ github.token }}`): `npm ci`, download the artifact, then `node scripts/release/publish.ts --dir <dir>`:
   - checks each tarball's SHA-256 against the plan, then uploads the uploads one at a time with `npm publish <tgz> --access public` (which authenticates through the trusted publisher; npm 11 attaches provenance). A version that reached the registry in the meantime fails `npm publish` with "cannot publish over the previously published versions"; the script re-checks the registry and treats a now-present version as published. Any other failure stops further uploads and fails the step after the record step has run for what is already on the registry;
   - the record step then runs for every package in the record plan, plus every package uploaded in this run, whose version `npm view` confirms on the registry (a lookup failure other than 404 fails the step; it never counts as absence): it creates a lightweight tag `git tag @indexyz/<name>@<version> <version commit>` when the tag is missing (no Git identity needed) and pushes exactly that ref (`git push origin refs/tags/<tag>`), and it creates the GitHub Release (`gh release create <tag> --target <record commit> --title <tag> --notes-file <section>`, the section read from `<record commit>:<pkg>/CHANGELOG.md`, so an accepted older tag's Release carries that commit's notes) when it is missing and the exact section exists there. A tag whose commit does not carry the version, or any other `gh` or `git` error, fails the step.

**Why this shape:** the plan job does everything that can fail without credentials, so a defective preparation never reaches `npm publish`, and a push that changes nothing ends in `plan`. Building each upload in a worktree at its version commit makes the artifact, the notes, and the tag describe the same reviewed snapshot: a retry after a failed upload publishes what the agent prepared, even if `main` has since received further changes to that package under a still-pending intent. Deriving tags and Releases from committed state instead of from "what this run uploaded" makes every entry point converge: a rerun of the original run, a "re-run failed jobs" (which reuses the artifact), and a dispatch on `main` all recompute the same uploads and record work. "Upload succeeded, tag failed", "A published, B failed", "Release creation failed", and "main advanced before the retry" are each repaired by any of them, and a package that was published long ago is tagged at its own version commit, never at the retry commit. The reference needed `source_sha` because it built from the checked-out commit; here the input is unnecessary and dropping it removes the question of which ref a dispatch runs on.

**Abandoned preparations.** Freezing a version at its commit has one consequence the runbook spells out: a version that never reached the registry cannot be repaired in place, because a later commit that fixes the package without changing the version does not change what that version builds. So a preparation on `main` whose snapshot fails the plan (a `files` entry that does not exist, a failing load, a missing section) is _abandoned_: the fix lands with its own intent, the next preparation bumps past the abandoned version (changesets bumps from the current manifest version, and the plan checks only the current version's section), and the dangling `## <abandoned version>` section stays as history. The same applies to a version superseded by a second preparation before it was published. Neither case is reverted on `main`; a revert to a published version is never necessary and the tag check tolerates it anyway (its Release, if still missing, is then created from the tag's own commit). The general "do not prepare again while a prepared version is unpublished" rule is relaxed only for an abandoned version, and a version may be abandoned only when the registry confirms it absent and the workflow has shown it cannot ship as it is (the plan failed for it, or its upload failed for a reason in the package itself); an uncertain upload outcome is retried, never abandoned. To keep this path rare, the agent runs the plan step locally in dry mode (`node scripts/release/plan.ts --dry-run`, which builds and verifies the upload but writes nothing to the registry or GitHub) on the release branch before handing a preparation over.

**Hand-edited or stale versions:** a version bumped without a changelog section fails the plan; a version bumped without consuming an intent is caught on pull requests by the gate (Decision 3) and, on direct pushes, by review. Publishing a never-before-published package that has a `## <version>` section is allowed by design: that is how a new package debuts.

**Trusted publishing:** nothing changes on npm. The design keeps the workflow file name and directory, adds no `environment`, publishes with `npm publish` (npm 11 handles OIDC and provenance itself; the tarball's `repository.url` names this repository, which provenance checks), and keeps each package's `repository.url`. The `publish` job is the only job with `id-token: write`.

### 3. A small per-package release-impact gate in `lint.yml`

**Choice:** `scripts/release/gate.ts` runs on pull requests (`lint.yml`, `fetch-depth: 0`) with `--base <base sha> --head <head sha>` and computes the merge base itself. It first validates every intent file at head (parseable front matter, exactly one release entry, a workspace package name, a non-empty summary). For each workspace package it lists changed paths under the package directory that are published: `package.json`, `README.md`, `LICENSE`, `CHANGELOG.md`, or inside a `files` entry at head. For every such package it needs one decision contributed by the pull request:

- an intent file added or modified between the merge base and head that names `@indexyz/<name>` (`none` counts as a decision), or
- a preparation: the manifest version differs between merge base and head, the head `CHANGELOG.md` has a `## <head version>` section that the merge base lacks, at least one positive (`patch`, `minor`, or `major`) intent naming the package was deleted (a deleted `none` intent never counts, since changesets does not bump for it), and the package's changed published files are limited to `package.json`, `CHANGELOG.md`, and `README.md`. Any other published file changed in the same pull request needs an intent of its own, so source changes cannot ride on a preparation.

A version change without the other preparation signs fails. Unchanged intents already on the base never count. Packages with changes only in `test/`, `openspec/`, or unlisted files need nothing. The failure message names the package, its changed files, and how to record a decision: `npm run change -- --<patch|minor|major> @indexyz/<name> -m "<summary>"` for a release, or a hand-written `.changeset/<id>.md` with `"@indexyz/<name>": none` and the reason for no release. The changesets CLI has no flag for `none`, and `changeset add --empty` writes an intent that names no package, so it would not count for any package; the runbook therefore shows the `none` file verbatim.

**Why:** `changeset status --since` only checks "any changeset exists", so one stale intent would let unrelated changes through. The reference's gate has the same per-package semantics; this is its reduction to what changesets' files express (no ledger, no withdrawal). It is a diff-based decision check, not a semantic classifier of bump types.

**External pull requests and direct pushes:** the gate applies to external pull requests too; a maintainer or agent adds the intent to the contributor's branch (or in a follow-up commit before merging). Published content that reaches `main` without a decision (a direct push, or a pull request merged before the gate existed, such as `52e5517`) gets its intent in the next pull request that touches the repository, before the next release of that package; the runbook says so.

**Testing:** the gate, the version-commit lookup, the changelog section extractor, the plan step's decisions (uploads, record work, tag-state errors, tarball inspection), and the publish step's decisions (upload outcomes, tag and Release creation) are TypeScript modules under `scripts/release/` (run by Node's type stripping, no build step) with pure functions separated from `git`/`gh`/`npm` calls, tested with Node's built-in runner (`node --test "scripts/release/test/*.test.ts"`; Node does not accept a bare directory) through the root `test:scripts` script that `npm run check` includes; history-dependent functions are tested against small fixture repositories created in a temporary directory. No new test framework at the root. The repository allows no JavaScript modules, so the tooling and `.changeset/changelog.ts` are TypeScript checked by a root `tsconfig.json` with every strictness option (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `erasableSyntaxOnly`, and the rest) and by `.oxlintrc.tooling.json`, a type-aware oxlint profile (through `oxlint-tsgolint`) with the `correctness`, `suspicious`, `pedantic`, and `perf` categories and strict typing rules; `npm run typecheck` and `npm run lint` include both. The profile is scoped to the tooling because applying it to the existing packages would be a separate change to published code.

### 5. What is removed

`scripts/check-workspace-versions.mjs`, the `check:versions` and `pack:*` scripts, the shared-version README section, the package READMEs' release checklists, and the tag trigger. No compatibility path keeps `v*` tags working; existing `v*` tags stay as history and no new one is created.

## Risks / Trade-offs

- **Registry absence authorizes upload** → the plan job requires a unique changelog section and passing checks for every planned version, the gate requires a consumed intent for version changes in pull requests, and the published artifact is the inspected tarball built from the version's own commit. A hand-bumped version in a direct push with a hand-written section would still publish; that is the owner's own act and is documented as such.
- **Two preparations of one unpublished version** → changesets would bump again (`0.1.44` then `0.1.45`), leaving a never-published `0.1.44` section and a version no run will revisit. The runbook forbids stacking: publish the first preparation before preparing again (rebuild it on its branch while unmerged; abandon it only under the rule in Decision 2 once on `main`); the plan rejects duplicate sections.
- **The version commit depends on first-parent history** → a version introduced on a side branch and brought in by a merge commit resolves to the merge commit (the first-parent diff is what introduced it on `main`); with a rebase merge it resolves to the rebased commit. Both are commits on `main` that carry the version; fixture tests cover linear history, squash, merge, a replaced version, and a reformatted manifest.
- **A worktree build per upload costs an extra `npm ci`** → uploads are rare (usually one package per release) and the cost buys snapshot correctness; the worktree is removed after packing.
- **Changelog format mixes old dated headings with new plain ones** → only new sections need exact `## <version>` headings; old history is left as is, the first run tags `0.1.43` without Releases, and the behavior is documented.
- **An intent naming two packages breaks `--ignore`** → one file per package, enforced by the gate and stated in the runbook.
- **External pull requests without intents fail the gate** → documented maintainer step; the gate message names the command.
- **Per-package pinned Pi versions differ** → the smoke load uses the package's own `node_modules/.bin/pi` when present and the root one otherwise; unifying versions is a separate change.
- **The plan job runs package tests twice** (`npm run check` at the head, then each upload's `prepack` in its worktree) → accepted; the second run is the one that guards the artifact and runs on the snapshot that ships.
- **Provenance names the run's commit** → npm's provenance attestation records the workflow run's triggering commit (`github.sha`); on a retry after `main` advanced it names a later commit than the tarball was built from. The tag and Release name the version commit; the reference repository has the same property. Documented in the runbook.
- **A version that fails the plan blocks the batch until it is superseded** → while a current version fails plan verification, every push's plan fails on it and nothing else is uploaded or recorded; the fix and the next preparation for that package should follow promptly (two merges, since the gate keeps source changes out of a preparation). A version whose plan passes but whose upload npm rejects does not block planning: earlier uploads in that run stand and the record step still runs for what is on the registry. The required local dry run exists to keep the planning window from opening at all. Stated in the runbook's failure table.
- **A worktree `npm ci` needs that commit's lockfile to be in sync** → true for every commit that passed `lint.yml`; the runbook's failure table names the error so an implementer recognizes it.

## Migration Plan

1. Land this change as one pull request: tooling, workflows, docs, removals, package OpenSpec roots, README updates, and the release decisions the gate requires: a `patch` intent for `@indexyz/pi-provider-sub2api` describing the footer cache-hit fix merged in `52e5517` (its README change rides on the same decision) and a `none` intent for each of the other five packages (README-only changes). No version changes, no positive intent other than that one, no live publication. The gate passes because every package with changed published files has a decision.
2. Verify locally before merging: `npm run check`, the gate against `origin/main`, the plan step in dry mode against the current `main` (expect no uploads and six tag items), and, after the changesets configuration is committed, a throwaway `npx changeset version` run on a scratch intent that is discarded with `git checkout -- . && git clean -fd .changeset`.
3. After merging, the owner confirms on npmjs.com that each package's trusted publisher names `publish.yml` with no environment. The merge itself runs `publish.yml`: nothing to upload, six `0.1.43` tags to create at `b997bd2` (record work), no Releases for them; every later push without a new version is a plan-only no-op.
4. The next release is prepared on request as described in `docs/releases.md`; the first push to `main` with a new version is the first independent publication (for `pi-provider-sub2api`, it ships the footer fix).
5. Rollback: revert the change commit. Published versions and the `0.1.43` tags are unaffected; `v*` tags would publish again only if the old workflow were restored.
