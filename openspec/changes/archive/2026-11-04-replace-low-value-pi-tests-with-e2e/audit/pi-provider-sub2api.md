## Findings

The suite passes in full while the first two of these are live defects. None of the existing tests can see them.

### Finding 1: `stream_read_error` is not retried by Pi 1.5.0

- **Claim.** README.md:386 says a relayed Codex `stream_read_error` is surfaced "so pi's own retry handling can retry the turn". c72042e deleted the extension's retry loop on that basis.
- **Result [V].** All three wire shapes ended the turn after one attempt, with no `auto_retry_start`:

| Relay failure                                    | Attempts        | Final error                      |
| ------------------------------------------------ | --------------- | -------------------------------- |
| SSE `error`, `code: stream_read_error`           | 1               | `Codex error: stream_read_error` |
| SSE `error`, `message: stream_read_error`        | 1               | `Codex error: stream_read_error` |
| SSE `response.failed`, `stream_read_error`       | 1               | `stream_read_error`              |
| SSE `response.failed`, `Upstream request failed` | 2, then success | none                             |
| HTTP 502 JSON, `Upstream request failed`         | 2, then success | none                             |
| HTTP 503, body `Service Unavailable`             | 2, then success | none                             |
| HTTP 503, body `upstream down`                   | 1               | `upstream down`                  |
| Stream closes before a terminal event            | 2, then success | none                             |

- **Cause [R].** `pi-ai/dist/utils/retry.js:51` matches only `upstream_stream_read_error`. The Codex adapter also drops the HTTP status from the message, so a 503 retries only if its body text happens to match.
- **Why the suite missed it.** `sub2api.test.ts` L1006 feeds the error through a mocked adapter and checks pass-through. It says nothing about the retry the user is promised.
- **Decision for the owner.** Either the package normalizes this error into something Pi retries, or the README promise goes. 56177b3 fixed this exact production failure before c72042e removed the fix.

### Finding 2: `/reload` keeps a stale credential and a stale stream handler

Sequence run in one RPC session, using an extension command that calls `ctx.reload()` [V]:

| Step     | Config change                                                    | Next generation request                   | Status    |
| -------- | ---------------------------------------------------------------- | ----------------------------------------- | --------- |
| Reload 1 | none                                                             | `/v1/responses`, `Bearer REAL-TOKEN-A`    | correct   |
| Reload 2 | token A to B                                                     | `Bearer REAL-TOKEN-B`                     | correct   |
| Reload 3 | token B to C, api `openai-codex-responses` to `openai-responses` | `Bearer REAL-TOKEN-B`; quota GETs use C   | **wrong** |
| Reload 4 | provider removed from `sub2api.json`                             | model still listed, `Bearer REAL-TOKEN-B` | **wrong** |

- **Mechanism [R].** `model-runtime.js:672-678` merges a re-registration over the previous one and keeps fields left undefined. index.ts:356 omits `streamSimple` when no model uses Codex, so the previous `streamCodex` stays attached. That closure holds the previous module graph's `relaysByProvider`. The package never calls `pi.unregisterProvider`, and `ModelRuntime` outlives the reload.
- **Impact.** After reload 3 Pi lists the model as `openai-responses` while the request carries the rotated-out token [V], and by the mechanism above it still goes through the Codex handler [I]. After reload 4 a removed relay keeps receiving prompts and a credential the user believes is gone [V]. Neither produces an error.
- **Related [I].** `/sub2api-refresh` reaches the same merge at index.ts:534, so an auto-routed relay whose last Codex model disappears should keep the stale handler within a session. Not run.

### Finding 3: tests whose names claim more than they check [R]

- `sub2api.test.ts` L1619, "...and no retries": the fetch never fails, so no retry path runs.
- `sub2api.test.ts` L1567, "does not publish an in-flight quota result": the final assertion is `not.toContain("stale · loading…")`, which also passes if the result is published. Only the abort check has force.
- `codex-compaction.test.ts` L405, the main replay test: it builds the replay with its own helper and options rather than the adapter's. The silent failure it should catch (prefix mismatch, native window not substituted) cannot happen there.
- `sub2api.test.ts` L930: guards buffering removed in c72042e. It now asserts the mock's own timing.
- `extension-load.test.ts` L60 and `npm run test:e2e`: with no `sub2api.json`, index.ts:96-99 returns before registering anything. Running that path returns `{"commands":[]}` with `success:true` [V]. So no test today registers a provider in a real host, and the load check cannot see `/openai-compress` vanish.

### Finding 4: documentation and coverage gaps [R]

- README.md:417 says discovery, billing, and quota requests retry up to twice. c72042e removed that.
- README.md:423 says compaction has a three-minute timeout. `COMPACTION_TIMEOUT_MS` is 300,000 since 796eeb2.
- 796eeb2 (five-minute compaction timeout) has no test. A real-time check would take over three minutes. Treat it as an accepted gap or a slow nightly job, not a blocker.
- c07193a (context overflow) lost its test when c72042e rewrote the file. Probe 2 confirms the behaviour works [V].
- An invalid checkpoint in the compaction hook (for example after switching model) has no test at all. README.md:384 promises it, and it should be added to S4.

### Answer: does module state survive `/reload`?

- **Issue #11287 does not apply.** It concerns `registerApiProvider` extension APIs wiped by `resetApiProviders()`. This package registers built-in `api` values through `pi.registerProvider`, and `provider-composer.js:378` dispatches directly to `extension.streamSimple` [R]. Reloads 1 and 2 worked [V]. The issue is closed as not planned; a maintainer could not reproduce it and notes Pi has no settings file watcher [R].
- **`relaysByProvider` does not survive.** `/reload` calls `clearExtensionCache` (`resource-loader.js:373`) and the loader uses jiti with `moduleCache: false` (`loader.js:482`), so every reload evaluates a fresh module graph with a new, empty map [R]. Consequences:
  - Toggles and ultra state reset on reload, as documented [V].
  - `relaysByProvider.clear()` at index.ts:173 clears an already empty map on a reload [I]. It still matters when a cached factory reruns inside one graph (`loader.js:466-470`) [I].
  - `nextExtensionGeneration` has the same scope, so it cannot detect staleness across a reload. `active` and `lifecycleController` do that work [I].
  - The old map stays alive only through the stale closure in Finding 2 [V for behaviour, R for mechanism].

- **KEEP**: needs no stand-in host, or needs only the fake `pi` removed in favour of a direct `loadRelayConfigs` call. Pure functions fed a minimal context (`renderUsageFooter`, `addServiceTier`) count here, and they cannot see a change in the real shape.
- **REPLACE-cheap**: the assertion stays; only the harness changes (local server, real loader or RPC).
- **REPLACE**: needs a multi-step scenario or a TUI.
- **DELETE (dup)**: an added category for a case with no failure mode that another surviving case lacks.

## Spec notes for the proposal

- `openspec/specs/real-environment-testing/spec.md` says every test SHALL drive the host. Pure tests with no stand-in, such as `credential-command` and `request-mode-store`, replace nothing but also drive nothing. The proposal should exempt them explicitly, or they fail the first clause.
- `docs/workflow.md` defers this package's "live-endpoint tests". The package has none [R]: every network call in `test/` is stubbed. The spec's local-server scenario needs no credential, so the deferral need not block S1 to S14.
- Exporting `parseRemoteCompactionStream` for direct tests would change a published file, which the spec forbids in a conversion. That is why parser cases go through a relay fixture.
- Catalog constants (`cost: 5`, `272000`, Grok `2/6`) fail on Pi upgrades with no user impact. Compare to the real catalog at runtime.
- RPC limits: no `/reload` built-in (use a small test extension calling `ctx.reload()`), `setFooter` is a no-op, and the relay must decode zstd.
- A real relay's `baseURL` is part of the discovery cache key, so S8 needs a fixed port across processes. Probe 2's random port caused a refetch that is correct behaviour.

## What was not verified

- S11 hooks, tool replay, xAI textual compaction, the Completions route, and all of S12 were not run.
- S2 was not run in a peer-less install; registration there rests on the requester's check.
- No mutation testing. "Catches" claims in the KEEP column come from reading the code.
- The E2E runtime per scenario was not measured reliably.
- Probes ran from the workspace `node_modules`, so peers were resolvable there.
